# GS41: TLA Djinni did not join after a won battle; every battle returned 0 (session GS41, 2026-11-16)

User (after GS40): "upon winning the djinn battle, it does not join the party...".

## Cause

main_routine.c runs a battle as `entrance = Battle_RunEncounterFar(entrance)` and stores it as
gMainRoutineWork.sequenceResult (1 won, 0 fled, -1 lost). Battle_RunEncounterFar is a far-call veneer to Func_081197f0,
an asm2c routine (its result is r0). link.py writes a veneer whose caller and target prototypes differ with
`adapter()`, and the target's prototype came from another C caller: battle/presentation/m8118430.c declares
`void Func_081197f0(s32)`. A void target makes the adapter return 0: **every battle reported 0**. After a Djinni battle,
Func_080d793c(1) joins the Djinni only when sequenceResult > 0, so none joined. (A lost battle also reported 0
instead of -1: Scene_ReturnFromSequence took the win path.)

## Fix

tools/wasm/link.py: a veneer whose prototypes differ and whose target is an asm2c routine enters the routine's
wrapper (a2cw_<addr>) with the caller's words and returns r0, as the GBA's veneer (a plain jump) does. 61 veneers take
this path ("veneer to asm2c (r0 kept) 61" in the build log). GS1 has no asm2c routines: its build is byte-identical
(game.wasm 305267e5, game.js 622631f8).
