# GS31: Map zoom's picture jittered at map edges (session GS31, 2026-11-04, bug fix)

User report (live site, build fa471e5, GS1 site build 1d2a4fb6f65558c0): "When unzoomed, when reaching the border of the
map, the whole decor flick back and forth because it tries to move when it can't." Then: "When I say unzoom, I meant the
wide view" and "I saw it in a dungeon". So: **Map zoom More / Most**, field maps (dungeons), near a map's edge.

Branch `worktree-agent-a4be33ad62c902936` (worktree `.claude/worktrees/agent-a4be33ad62c902936`), on fa471e5. Not
merged, not deployed.

## 2. Root cause

GS29's frame placement (port/pc/ppu.c `zoom_frame`, at line 0 of each frame) reads the GBA's camera (gMapGridWork viewX,
viewY and its min/max bounds) **from game RAM at line 0**. The picture's BGs come from the BG registers, which the
VBlank copies from gBgScroll; after the VBlank the game's logic runs on (in the port it runs at once, before line 0)
and moves the camera for the *next* frame. So at line 0 the camera in RAM is one frame ahead of the BG registers being
drawn (the table above: the frame drawn after f2042 uses viewY 303 against BG1VOFS 304). Where the frame is centred
(XO, YO constant) this does not matter; where it is held at a map's edge, XO/YO = bound - camera, so the placement
used the new camera while the BGs showed the old one: the picture moved by the camera's last step, and back on the next
frame when no new whole pixel was crossed. While the camera moves a pixel every frame the picture was simply offset by
one pixel (no visible flicker); while the camera eases (starting, stopping, pushing into an edge) it alternated.

The GBA's own camera does not jitter (gBgScroll and viewY move monotonically in every run: the game logic is unchanged
and not involved; no translated or asm routine is on this path, so no D20 differential applies). The pre-GS29 builds
(6d08d4c8, before 1efad3f; GS27's Wide view) had no edge placement: Wide view always centred the GBA view, so the
decor could not jitter there (by the code; only its black past-the-bounds columns came from the same line-0 reads, so
at most the black edge could step a pixel). The bug came with GS29's placement (54edecb). Frame pacing is not
involved: the node runs are frame-exact and show it.

## 3. Fix (one commit; port/pc/ppu.c, GS1 renderer only)

The camera is taken at the VBlank, the same moment the BG registers are loaded from gBgScroll:
- `zoom_camera_snapshot()` (new, next to `zoom_frame`): reads gMapGridWork's viewX/viewY/min/max into statics.
- `Port_PpuVBlank()` (GS1 branch) calls it last (hw.c calls Port_PpuVBlank at line 160, before the VBlank interrupt's
  handler and before the game's next logic).
- `zoom_frame()` uses the snapshot instead of reading RAM at line 0.

Normal is unchanged (zoom_frame is not called; the snapshot only fills port statics). TLA's renderer (the
`#ifdef PORT_GAME_TLA` half) is untouched. Diff: ppu.c +25 / -11, all inside the GS1 half (the comment block
"GS31: the camera as it was at the last VBlank" through `zoom_frame`, and one line at the end of the GS1
Port_PpuVBlank).

## 4. Regress case that catches it

- `tests/probes/zoomjitter.cjs` (new, test-only): between JIT_FROM and JIT_TO, the best whole-picture step (dx, dy in
  -4..4, sampled; frames that match no step within 8% or only at +-4 are skipped: fades, menus, scene effects), reversals
  counted unless the GBA's camera itself turned back (hops); "CHECK FAIL" when any reversal is found or the route spent
  fewer than JIT_MIN_EDGE (30) zoomed frames at an edge.
- tools/regress.sh: cases **zoom_edges_most** (kolima_glade's route from kolima_grind.sav at Most) and
  **zoom_edges_more** (bilibin_ice's route from bilibin_cave.sav at More), with picture digests at the zoomed size; a log
  line starting "CHECK FAIL" now fails a case; `--quick` skips the zoom_* cases when picking the newest story cases.
- On the old build both cases fail ("377 reversals", "24 reversals"); on the fix they pass.

## 7. Merging with GS30

GS30 works in port/pc/ppu.c (World Map zoom). This fix touches only `zoom_frame` (its camera reads), adds
`zoom_camera_snapshot` and its statics just above it, and one call at the end of the GS1 `Port_PpuVBlank`. If GS30
adds its own camera/placement reads at line 0 for the World Map, they should take the same VBlank snapshot (or their
own taken in Port_PpuVBlank) for the same reason. expected.tsv will need rewriting again after the merge (any code
change moves the unmasked RAM rows); the zoom_* cases' CHECK FAIL is build-independent.
