# GS27: in-game "Extra settings" (colours, brightness) and the optional "Wide view" (session GS27, 2026-11-04)

The user asked (verbatim): "In GS1, Add the color settings to the game settings' menu. Then add an option to widen the
camera port to see more of the map." Asked where, the user said the colour settings go in the game itself: a game-style
settings screen drawn with Golden Sun's own windows and font, reachable from the in-game menu, not only the page's menu.

Branch `gs1-options` (worktree `~/golden-sun-wt/gs1-opts`), two commits, one per feature (rule 7). Both options are off by
default; with them off the game behaves as before (section 4).

## 1. Feature 1: "Extra settings" in the game

**Where.** Golden Sun already has a settings screen: START on the field opens the Pause menu (Save your quest, Sleep,
Change settings), and Change settings sets the window colour and brightness, message speed, speech and auto-sleep. Its
window is full (14 rows), the Pause menu's rows are its own messages and icons, and saving a quest goes through the Pause
menu in nearly every regress route, so adding a fourth Pause menu row would change the window, the cursor wrap (UP from
the top) and the RAM of every save route. Chosen instead, the least invasive reachable spot:

- **R on the Pause menu** opens Extra settings (R did nothing there);
- **R in Change settings** does too (it leaves Change settings as B does), and Change settings now shows a small window
  "R: More" at the top right, joined to its help window (the help line itself has no room: its messages measure 144-201
  of 208 px);
- B or START in Extra settings returns to the Pause menu.

**The screen** (`port/pc/options.c`, our code; it calls the game's own functions and copies none): a help window and a
three-row window (Window_Create, Window_DrawDividerLine, Text_DrawStringAtOffset / Text_DrawString with the game's font),
the pointing hand (gPointingHandTiles, WindowSprite_Create, MenuCursor_*Far moving it like the game's menus) and the game's
"Setup" heading (MenuTitle_Create(7), as Change settings shows it). Up/Down pick a row, Left/Right/A change it, with the
game's cursor/confirm/cancel sounds (the SE_ ids are passed from the vendor caller so they track the vendor's enum).

| row | values | page key | what |
|---|---|---|---|
| Screen colours | Original / GBA LCD | `gs-lcd` | the GS10 LCD curve (higan/bsnes) on the canvas copy |
| Brightness | Normal / Bright / Brighter | `gs-bright` | new: output gamma 1/1.25, 1/1.5 in the same LUT |
| Wide view | Off / On | `gs-wide` | feature 2 (GS29: now Map zoom, `gs-zoom`) |

**Hooks** (`port/c_rules.tsv`, build-time text rules on the vendor C, nothing copied): the R test in PauseMenu_Choose
(result `PORT_PAUSE_EXTRA_SETTINGS` = 0x40, past every real entry), PauseMenu_Run running the screen and reopening the Pause
menu, the R test in SettingsMenu_Run (result -2, edits dropped as for B), the "R: More" window and its close.

**Page sync** (`port/web/main.js`): the values belong to the page (presentation only; game memory, hashes and link
sessions are never affected). At each module start the page pushes them in (`Port_OptSet`); each frame it polls
`Port_OptGeneration` and applies in-game edits to its menu (checkbox / select) and localStorage (try/catch; default values
store nothing). The page menu's controls write back with `Port_OptSet`. Test overrides `?lcd=`, `?bright=`, `?wide=` (not
stored). The page menu says "In the game: START, then R opens these picture settings too."

**Input**: keyboard and the touch pad drive the game's keys (the screen reads the game's key state), so both work. The
page has **no gamepad input at all** (main.js only mentions gamepads as a future source of the same key state); nothing
was added here, so "gamepad" works once the page reads gamepads.

## 2. Feature 2: "Wide view"

**Replaced in GS29 by "Map zoom"** (docs/GS29.md: 3:2 frames, the page box never changes); this section is the history.

**Size: 288 x 160** (the GBA's 240 in the middle, 24 px = 3 tiles on each side). 1.8:1, a little wider than 16:9 (284.4 x
160); chosen for whole-tile, symmetric margins (the map is drawn in 8 px tiles and 16 px cells) and an even width for
canvas scaling.

**What widens: the field sequence's maps only** (`port/pc/ppu.c`, GS1 branch):
- The centre 240 columns are drawn exactly as before, from VRAM.
- The GBA's text BG maps are 32 tiles (256 px) wide and the game streams one column at a time around its 240-px view, so
  the margins cannot come from VRAM. They come from the map grid in game RAM: the 128 x 128 cells at 0x02010000 and the
  cell pictures at 0x02020000, the same tile entries MapGrid_RenderCellPicture* write into the BG maps. Map layer i is
  BG(3-i) with its map in screen block 5+i; its full scroll is gBgScroll plus the line's register offset (9-bit delta),
  so per-line scroll effects carry over.
- A map layer's margins are used only on lines where the BG map's first and last visible columns equal the cells there;
  otherwise (a scene drawing its own pictures into those BGs) the layer is empty in the margins.
- Margin columns past the map's camera bounds (gMapGridWork: viewX, minX, maxX) are black; the camera itself is **not**
  moved (moving the clamp showed BG columns the GBA never shows on 256-px-wide scenes such as the title), so at a map's edge
  one side shows black.
- The window layer (BG0) stays centre-only, so windows and text stay in the middle.
- Sprites: OAM x up to 263 is drawn in the right margin and 488-511 in the left one. The game's culling is widened by
  `gPortWideMargin` (24, or 0 when off): the field camera's actor test (actor_camera.c), Actor_GetScreenPosition (actors.c)
  and Sprite_Draw's right-edge test (sprite_draw.c), all c_rules; with 0 each test is the original.
- Window registers (WIN0/WIN1) in the margins use the edge column's result.
- Which frames: `FieldSequence_Run` marks entry/exit (c_rules; a reset also clears it, main.c) and
  `MapGrid_UpdateLayerScroll` stamps each field frame; a frame widens only inside the field sequence with a stamp no older
  than 2 frames.

**What stays 240 wide (black side bars)**: battles, the World Map, the title, naming and File screens, the credits,
anything outside the field sequence. Full-screen menus over the field (Psynergy/Item/Status) keep the field visible in the
margins while their tasks run (the field's map task stamps them); they are drawn centred.

**Frame and page**: with the option on the frame is 288 wide for every screen (`Port_FrameWidth`), so the canvas never
changes size between scenes; it changes at once when the option is toggled (no reload). main.js resizes the canvas and
ImageData, CSS `#screen.wide` (288:160, up to 864 px), and touch.js lays out the picture from the canvas's aspect ratio in
portrait and landscape. tests/boot.cjs captures at the frame's width and takes `--opt I=V@F`.

**The Lost Age** shares ppu.c and main.c (port/tla/pc.tsv): ppu.c holds two renderers, `#ifdef PORT_GAME_TLA` the one as
it was, so TLA's build is byte-identical to one without GS27 (checked; see 4). Keep both renderers in step.

## 4. Options off: the game as before

`tools/regress.sh`'s RAM digests are **build-specific**: the game keeps wasm function table indices and pointers into the
module's own data (relocated buffers) in its RAM, so any change to the code or data layout changes them. The committed
expected.tsv matches main's build/wasm only because that build still links a stale `probe_tmp` object (Port_ProbeMsg; trap
below): a clean build of HEAD be42a96 (game.wasm SHA-1 fdd0e5e2...) already gives "DIFF" on every RAM row.

So the check here compares builds directly. `tests/probes/digest.cjs` takes `MASK_CODE=1`: words in 0x10000-0x1ffffff (table
indices and module data pointers) count as 0. Full regress (all 61 node cases and link2, in four chunks with REUSE=1):
1. clean HEAD build, `MASK_CODE=1 tools/regress.sh --update` (expected.tsv restored afterwards);
2. this branch's build, `MASK_CODE=1 tools/regress.sh`.

Result: **every RAM digest and every picture digest of all 61 cases is equal**. 28 save rows differ, and only in words that
are module-data pointers the game writes into its save (sol_star_room: 37 bytes, one value 0x88d2c -> 0x908bc in 9
places; loading a save and saving again keeps the loaded value). link2: 20/20 checkpoints agree, b won, on both builds (its
own RAM digests are unmasked, build-specific).

**Finding for main (not changed here):** the save holds a pointer into the module's data (relocated buffer). A save made
with one deploy keeps that build's pointer; after a deploy that moves the module's data, a loaded save points elsewhere
(whatever reads it gets other data). Worth a look: which structure is saved with it, and re-deriving or relocating it on load.
**Fixed in GS28 (section 8):** the saved actor snapshot's script/update words; saves now hold GBA addresses, old saves migrate.

## 6. Traps

- **Stale objects are linked**: the wasm build links every object left in build/wasm*/obj, also those of deleted or renamed
  port files (main's build/wasm still has `probe_tmp.ll.o`; a renamed file left `ppu_tla` objects here). Compare builds only
  after `rm -rf build/wasm` (or delete the stale ll/bound/obj files).
- A frame-to-frame jump of the field camera of more than 8 px leaves stale BG map columns (MapGrid_UpdateLayerScroll
  draws one column per 8-px step); found when the camera clamp was widened at once. The final design never moves the camera.

## 8. GS28: build-independent saves (the finding of section 4, fixed; 2026-11-04)

**What held the pointers.** The second half of the save buffer holds `gActorSnapshot` (0x02001104, `struct
ActorSnapshot`: 32 slot bytes, then 32 `struct Actor` of 0x70 bytes). Actor_Snapshot (field/field_sequence/actors.c)
DMA-copies up to 32 live actors there before a random battle and when the game is saved (Save_CaptureActorsFar), and
Actor_Restore copies them back when the party keeps its place (Continue, after a battle). Two fields are wasm values in
the port:
- `script` (+0x00), the actor script: when the script is a relocated data symbol (D19: it holds code pointers), the
  game got it from a relocated table, so it is the module's reloc_* buffer. sol_star_room's statues run
  `380_gSolSanctumElementalStarRoom_AngleScript`: GBA 0x0200cbd0 (overlay 0x380's area), live build 687968a7 0x88d4c,
  main be42a96 clean 0x88d2c, gs1-options 1a0c602 0x908bc (the 9 words of section 4: six statues, two copies of part 3).
- `update` (+0x6c), a callback: a function table index (Vale's `ov373_Scene_UpdateFloatingNut` = 0x10172 in
  vale_day1.sav). The GBA stores the code address (0x0200dae1). Indices happen to be equal in every build so far.
Proof: saves of the same route on two builds differ only there (section 4's 28 rows, and the 46 saves below); a pointer
scan of all 61 regress saves finds no other build-specific words (the other hits are game data, equal on all builds).
The 32 entries past the list's end (slot 0xff) are older snapshots' actors: saved too, never read.

**Fix (port side only; port/pc/save_compat.c + 3 c_rules on actors.c, vendor code untouched).** The snapshot holds the
GBA spelling: Actor_Snapshot ends with Port_ActorSnapshotToGba (buffer -> its symbol's GBA address, table index -> its
function's GBA address | 1); Actor_Restore copies each actor from Port_ActorFromSnapshot, a copy with this build's buffer
(for the main image or the overlay now loaded, which port/pc/decompress.c reports) and table index. The live actors
never see GBA spellings, so nothing else changes. A GBA/emulator save's values are what the port now expects.

**Migration.** Actor_Restore first calls Port_ActorSnapshotMigrate: a script in module data is read as a buffer of the
live build 687968a7 (its 412 buffers, port/pc/save_legacy.h, made with tools/reloc_map.cjs from main's build/wasm), else of
main be42a96 clean (same layout 0x20 lower: 687968a7 also links probe_tmp's data), else of gs1-options 1a0c602 (0x7b70
higher); listed actors only for the main image and the loaded overlay, the stale entries for any. A table index is read
as 687968a7's (its 5,350 code map indices, tools/code_index_map.cjs). The snapshot itself is rewritten, so saving again
writes the GBA spelling. Where builds' ranges overlap the live build wins (12 start addresses are ambiguous between
687968a7 and be42a96-clean; be42a96-clean was never deployed).
