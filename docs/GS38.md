# GS38 — 2026-11-13: The Lost Age no longer kills the page on iPhone (a2c_dispatch in groups)

User: "GS TLA is reloading, that's probably a memory leak or high CPU crash similarly to Conker's menu problem" ...
"the game crashes like 30 seconds after starting during the first 'cinematic'".

## Cause

The same as Conker's P387. iOS browsers all run WebKit (JavaScriptCore). JSC optimizes a hot wasm function with its
OMG tier only when its cost is under `maximumOMGCandidateCost` (100000). TLA's `a2c_dispatch` (tools/wasm/asm2c.py:
one `switch` over the 1362 addresses of the translated routines, 621 of them with an overlay `switch` inside, a call
in every case) was 93.6 KB of wasm after Asyncify, just under that limit. It is called on every indirect jump, so it
gets hot within the opening; OMG's B3/Air passes then take about 2 GB for it, and iOS kills the WebContent process
(Chrome on iPhone reloads the page).

Measured in a WKWebView on macOS (same engine): a Swift runner (scratchpad, not in the repo) loads a local page whose
worker runs the rtw module (`retrowser/tla/tla.js`) at 59.73 fps with the regression routes' keys (new_game,
opening, ...). The WebContent footprint is sampled every 2 s (`footprint`), the peak read with `vmmap --summary`, and
the process sampled with `sample` during the spike. JSC options reach the WebContent process as `__XPC_JSC_<option>`
environment variables.

| build, JSC options | WebContent peak |
|---|---|
| published (before), defaults | **2.5 GB** at ~2 min (frame ~7200, the opening); `sample`: a Wasm Worklist thread in `OMGPlan::work` -> `B3::prepareForGeneration` (fixSSA, generateToAir) |
| published, `useOMGJIT=false` | 247 MB |
| published, `maximumOMGCandidateCost` 2000 / 10000 / 40000 / 70000 / 95000 | 254 / 255 / 382 / 380 / 400 MB |
| this build, defaults, 150 s | 399 MB |
| this build, defaults, 300 s (frame 18720) | 307 MB |

Only functions costing 95000-100000 make the spike, and the only one there is the old `a2c_dispatch`. (A first
attempt to find it in the jsc shell, the module run headless with `jsc_tla.js`, was misleading: the shell's peaks vary
by ~150 MB from run to run and it never tiered the dispatch up as the page does.)

## Fix (tools/wasm/asm2c.py, tools/wasm/build.py)

The dispatch is emitted in groups of about `DISPATCH_GROUP` (32) calls, by address: `a2c_dispatch_gN(a)` holds its
cases' `switch` and returns 1 when it called a routine. `a2c_dispatch` picks the group with a comparison tree on the
groups' first addresses, calls it through one function pointer, and falls back to `a2c_call` as before. The groups
are now 45 functions of at most 2.7 KB each.

- The pointer is needed: with direct calls, wasm-opt's `-O2` at link inlined each group (each has one caller, and C's
  `noinline` does not reach wasm-opt), which rebuilt the single 93.6 KB function.
- The tree sets the pointer in code. A data table of group pointers (consecutive table indices, 65536 + n) equals 16
  bytes of `encounter_rules` ROM data, and the leak check refused the build. So did a table of group start addresses.
- `split_asm2c` now finds the dispatch by the line `asm2c.DISPATCH_MARK` (a comment written before the groups), so the
  groups go to the last unit with the dispatch.

GS1 is not affected (asm2c is TLA only): GS1's rtw build id stays 1df366983f93b071.

## Watch for

Any generated function between about 10 KB and 100 KB of wasm with hundreds of call sites (Asyncify makes each one
~70 bytes) that becomes hot. Sizes: `node wasm_funcs.cjs tla.wasm` (name section). To profile in WebKit, use the
WKWebView runner with `__XPC_JSC_maximumOMGCandidateCost=N` to bisect by size.
