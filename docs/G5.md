# G5 field notes (session GS5, 2026-11-01)

Session notes for GS5: the storm-night colours were checked, a RAM readout was added for routing, and the
prologue route goes on past the first rock. These are G4 phase steps; the file name is the session's, not the
phase's.

## 1. Vale's storm night is bright: the game's own colours, not a port bug

Report: GS4's captures of Vale on the storm night (`port_work/g4/sheet13.png`) are bright yellow-green, while the
night on hardware looks dark.

What the game does: Weather_StartLightning (weather.c) builds the night colours with
`PaletteFade_Build(PALETTE_TINT_WARM, ...)`: per BG colour, R/2 + 10, G - G/3 + 8, B - 7, clamped to 0..31, then
mapped through the ROM's three channel curves (gColorBuffer_ChannelCurve/Light/Contrast). The lit colours come
from PALETTE_TINT_PALE. Weather_UpdateLightning shows the lit colours for one frame, three times 5 frames apart,
and each time fades back to the night colours over 12 frames. OBJ colours stay untinted (Isaac's sprite).

Checks, all on the current build:
- **Palette RAM = the game's formula**: `tests/boot.cjs --probe` at frames 3000 (house) and 5000 (Vale): all
  224 BG colours equal PALETTE_TINT_WARM of the scene's source palette (gPaletteFadeWork->palette), recomputed in
  JS from the ROM's curves.
- **The compiled code = the ROM's code**: new diff spec `PaletteFade_Build`: the vendor C compiled to wasm vs the
  ROM's Thumb code in the D20 interpreter, through a new test hook `Port_CallCode4` (call_via.c). **EQUIV, 1200
  cases** covering every per-colour mode (NONE, GRAYSCALE, SEPIA, WARM, MUTED, PALE, RED, WARM_DARK, default,
  CUSTOM, BLEND, SPLIT) on random palettes, all three halves. Negative control: swapping WARM for WARM_DARK on
  the port side fails (2476 bytes differ).
- **No hardware darkening is asked for**: Vale shows BLDCNT 0x3f00 (no brightness effect), BLDY 0, no window
  effects. The house (f3000) uses BLDCNT 0x3f42 with EVA 0 / EVB 16 (alpha on BG1: the roof layer hidden).
- **Lightning plays**: palette changes at bursts (for example frames 5478-5500); `port_work/g5/storm/sheet.png`
  shows the night (f5470), the flash (f5478) and the fade back (f5483, f5488, f5495).
- PPU colour expansion is the usual `c << 3 | c >> 2` (ppu.c).

Conclusion: the colours are what the ROM computes; there is nothing to port or fix in the game logic. The night
palette is a warm yellow-green on purpose; it is not a dark blue night. It looks darker on a real GBA because
the original GBA's LCD (no backlight, strong gamma) shows everything much darker than a PC screen; emulators offer
"GBA colour correction" for that. If the user wants this, it is an **optional display filter** (orchestrator rule
7: a page setting, default off) in the page's canvas output, not a change to the game. Not done: it is a page
change and a decision for the user.
Captures (gitignored): night `port_work/g5/storm/frame_05470.png`, flash `frame_05478.png`, sheet `sheet.png`.

## 2. Routing tools (test only)

| | |
|---|---|
| `tests/boot.cjs ... --probe FILE[,FILE]` | per-frame hook modules `(m, frame, keys) => void` |
| `tests/probes/where.cjs` | prints scene id + name, entrance, map id, leader x/y/z and 16-pixel cell whenever scene/entrance/cell changes (`WHERE_EVERY=N` adds every N frames) |
| `tests/probes/mapdump.cjs` | `MAP_AT=F` prints the cell behaviors around the leader as ASCII (`#` wall, triggers by id in base 36); `MAP_MODE=height` prints the first height samples instead; `MAP_W`/`MAP_H` |
| `tools/route.sh FRAMES "KEYS" keyfile...` | boot + where probe; `FROM=F` filters lines, last frame to `port_work/g5/route/` |

RAM used (from the vendor headers; addresses are in port/symbols): gMainRoutineWork 0x02000240 (`next` scene
+0x1c0, `entrance` +0x1c2, `mapId` +0x1da); gFieldWork 0x03001ebc -> FieldWork.actors[0] (+20) = the party leader
(Actor_Lookup(ACTOR_PARTY_LEADER)); Actor x/y/z at +8/+12/+16 (16.16 pixels), layer +36; map cells 128 per row
at gMapGridCellBuffer 0x02010000 (4 bytes: picture+flags, behavior, shape), shapes at gMapGridShapes 0x0202c000.
Scene names come from the vendor's `field/scenes.s` row order (read at test time, not copied).
No input recorder in node: the page is where people play, so the page's recorder belongs to G4's e2e work.
