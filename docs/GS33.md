# GS33: "Menus: Edges": on a zoomed map, windows pinned to the picture's edges (session GS33, 2026-11-04/05)

User report (phone screenshot, GS1, Map zoom Most, a Kolima-area forest field map near its top edge, so the GBA's view
sits low in the frame; field menu open): the party status window (Isaac/Garet/Ivan HP/PP) floats in the middle of the
picture and the command icons + "Psynergy" window sit above the bottom edge, because windows are drawn in the GBA's
240 x 160 inside the bigger frame. The user's choice: **"Pin to edges"**: while the map is zoomed, each window moves to
the nearest edge of the wide picture (top part to the frame's top, bottom part to its bottom, sides to the sides), the
same size, for every window (field menu, status, dialogue, shops, Psynergy/item/Djinn menus, Pause and settings, name
tags), on field maps and the World Map at More/Most.

On `main`: d92eb27 (feature), a719675 (expected.tsv), then the docs. **Not deployed, not pushed.**

## 1. Phase 1: how GS1 draws its windows (findings)

Read from the vendor source (vendor/alchemy/games/tbs: include/window/window.h, include/graphics/render_input.h,
src/window/window/{windows,sprites,borders,text_tiles,glyphs,selection}.c, src/window/screens/{icon_menu,menu_titles,
joined}.c, src/system/system/{oam,frame,heap}.c, src/field/field/sprite_draw.c) and measured in node (scratch probes in
port_work/gs33: window slots, OAM entries with their source, at the field menu, its screens, Pause, Extra settings, the
World Map menu, Imil's dialogues and shop).

**The window layer.** Every window is a bordered rectangle of one text BG, the window work's 32 x 20-tile tilemap
(`WindowWork.tilemap`), copied to **screen block 4 (WINDOW_TILEMAP_VRAM, 0x06002000)** by the VBlank task
`WindowSystem_UploadTilemap` (bands of four rows that changed). On the field and over the World Map's still picture it
is **BG0** (BG0CNT 0x0400: priority 0, char block 0, screen block 4); the map is BG1-BG3 (World Map moving view: mode 2,
BG0 not shown, no windows then). Labels drawn at once (`Text_DrawMessageAsTiles`, text_tiles.c; also glyphs.c,
name_entry.c) write their tiles **straight into VRAM's tilemap**, not through the VBlank upload: a new window's text
shows a frame before the VBlank sees the window (measured: the field menu's status text at f2002, its window in the
VBlank's RAM from f2003; on the GBA too the text comes a frame before the border).

**Window structs in RAM (the reliable source).** `gWindowWork` (IWRAM 0x03001e8c = heap slot 15 of gHeapSlots
0x03001e50) points at `struct WindowWork` (international: 4,860 bytes): `windows[8]` at +0x500, 0x24 bytes each:
sprite list head (+0), width, height, **x, y in tiles** (+8, +0xa, +0xc, +0xe), `opened` (+0x10), `flags` (+0x16),
`zoomStage`/`duration` (+0x18/+0x1a). `Window_Create` fills x/y/w/h, opened = 1 and flags at once (the zoom-open
animation draws smaller rectangles inside that final one; closing keeps the slot until it has shrunk). A slot is live
while opened, flags or duration is non-zero. Off-screen windows exist (a shop's portrait window at x = -5 tiles).
Measured layouts: field menu = status (11,0,19,5) + "Psynergy" label (18,17,9,3); Psynergy/Item/Djinn/Status screens =
5-6 windows tiling the whole screen; Imil's shop = question (5,0,20,3), price (0,8,15,4), coins (18,7,12,4), item row
(0,12,30,4), description (0,17,30,3); dialogues: placed 32 px above/below the speaker (messages.c), or by flags.

**Which OAM entries are menus.** Everything that draws a sprite links an entry into one of 256 depth slots
(`Oam_AddSpriteAtDepth`); `Oam_BuildBufferKernel` (our C port, port/pc/oam_kernel.c) walks slot 255 down to 0 into the
frame's OAM list, which the VBlank copies into OAM. So the queued entry's **address** says who drew it:
- the windows' own sprites: the 64 `WindowSprite`s at WindowWork + 0x698 (28 bytes; the queued cell is the link at
  +0x10): letters (depth 254), the page arrow, portraits, the pointing hand (`MenuCursor`), the bobbing menu headings
  ("Pause", "Settings": `MenuTitle_Create`, two WindowSprites at 253), command icons of Change settings (251). Each is
  on its window's sprite list, so its window is known.
- menu work in heap slots: party status (16), selection screens (18: shop/Psynergy item rows, arrows, the hand; 238-248),
  selection workspace (19), settings (20), menus (55), battle menu (57), **icon menu (58: the field menu's command
  icons, 245/246)**.
- bare entries that are C locals (outside GBA RAM in the port, trap 80): the "joined" portrait (250), a scene's arrow.
- the menus' party members (Psynergy/Item/Djinn/Status screens): ordinary field `Sprite`s from heap slot 4 placed by
  `Render_ApplyProjectedPlacement` at depth 251, inside their window.
- not menus: field actors (slot 4/5, depth = screen y / 2 + 10, 0 and 2 for shadows; measured up to ~130 with zoom),
  World Map actors (projected, depth (512 - z) / 2 + 128, measured up to 184), weather (slot 29, 240), ground marks.
The renderer tells UI from map content by these sources (tags written by the kernel, read at the VBlank), never by
priority, palette or position.

**When.** The VBlank copies the OAM list and uploads the tilemap built by the logic that just ran; the logic for the
next frame then runs before the next frame's line 0 (trap 93). So the OAM tags, sprite lists and window rectangles are
read in `Port_PpuVBlank` (the same moment as GS31's camera); the windows are completed at line 0 with those opened since
(their text is already in VRAM, above).

## 2. The anchoring rule (decided) and what was built

**Rule.** Per axis, windows are grouped: across, windows side by side that touch or overlap and share rows; down,
windows stacked that touch or overlap and share columns (a full-screen menu is one group each way; Imil's price window
and the item row below it are one group down). A group's extent [a, b) on the GBA's screen (S = 240 across, 160 down)
gives its anchor:
- touches exactly one edge -> that edge (status window at the top right -> the frame's top right corner);
- touches both -> centre (a full-width dialogue, a full-screen menu);
- touches neither: b <= S/2 -> low edge, a >= S/2 -> high edge, spanning the middle -> centre.

Edge: the window moves by the frame's margin on that side, so it touches the frame's edge. Centre: it keeps its offset
from the frame's centre (where the frame is centred on the GBA view this is no move; near a map edge it re-centres).
A group keeps the anchor of its oldest window while that window stays open, and a window opening into a group takes the
group's, so **nothing jumps while open**; the offsets are recomputed each frame from the frame's place (the VBlank
camera, GS31), so an anchored window stays still in the picture even while the camera moves. Anchors come from the
windows only (not their sprites, which can arrive a frame later and would otherwise flip a decision).

**Sprites belonging to a window** move with it: the window under the sprite's centre, else its own window (list), else
a window within 8 px, else a menu sprite within 8 px that already has one (the field menu's icon row joins the
"Psynergy" label). Menu sprites with none of these stay where the game put them; the field sprite pool's depth-251
sprites count only inside a window. A cursor moving between windows follows the window it is over.

**What does not move and why**: the map layers (BG1-BG3, the World Map's affine BGs and still picture), every actor
and shadow, weather, effects: only window-layer pixels inside live window rectangles and tagged menu sprites are moved.
Checked pixel by pixel (scratch movecheck.py): Edges vs Centre at Most on the menu route (98 frames) and Imil's route
(78 frames) differ **only inside the menus' rectangles and sprite boxes (old or new place): 0 pixels elsewhere**.
Window-layer content outside every window (none seen) stays at the GBA's place.

**Dialogues**: moved like every window (the user's choice), so a dialogue placed 32 px above/below its speaker can move
away from the speaker near a map's edge; a full-width one goes to the bottom (or top) centre of the picture.
**Opening/closing**: the zoom animation draws inside the window's final rectangle, so it plays at the moved place; the
text that comes a frame early appears there too. **Straddling windows** keep their place relative to the frame's centre.
**Interiors smaller than the frame** (black around the map): windows move into the black margins and are drawn there
over black.

**Built** (d92eb27):
- port/pc/oam_kernel.c: `gPortOamSrc/Depth/Words/Count`, written by the kernel (port data, not GBA RAM; the game never
  reads them; D20 compares GBA RAM only).
- port/pc/ppu.c (GS1 branch): `menu_snapshot` (Port_PpuVBlank), `menu_layout` (line 0, after the frame's size and
  place), the window layer drawn from moved windows on every frame row (`menu_row_sources`, margins included), menu
  sprites placed as on the GBA and moved, a moved pixel's WIN0/WIN1/OBJ window taken at its source pixel, moved menus
  drawn over the black past a map's bounds. Work arrays are statics: as locals on the wasm stack they changed the
  garbage an uninitialised vendor local copies into GBA RAM (Message_OpenWindow's bounds[] for lines a message does not
  use, 0x020330e8 at bilibin f6900), which broke masked regress RAM rows at Normal (trap 96). Test hooks
  `Port_MenuWindow`, `Port_MenuSprite`.
- port/pc/options.c: Extra settings row 4 **"Menus" Centre / Edges, default Edges** (the user asked for it; rule 7 says
  optional, so it is a toggle), help "Zoomed map: menus at the edges."; `Port_MenusEdges`.
- page: "Menus" select (Edges / Centre), key `gs-menus` ("0" stores Centre; Edges stores nothing), `?menus=0/1` for tests,
  synced both ways with the game's row (GSOpts), hidden on the TLA page.
- Normal (240 x 160) and Centre never lay anything out (the VBlank read only fills port statics).
