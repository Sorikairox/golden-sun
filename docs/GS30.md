# GS30: Map zoom on GS1's World Map (session GS30, 2026-11-04)

GS29's Map zoom (Normal 240 x 160 / More 288 x 192 / Most 336 x 224, key `gs-zoom`) covered field maps only; battles and
the World Map stayed 240 x 160. This session asks whether the World Map can zoom too, without changing game logic.

## 1. Phase 1: how the World Map is drawn (findings, before building)

Read from the vendor source (vendor/alchemy/games/tbs: src/field/field/world_map.c, view.c, world_map_lines.c,
include/field/perspective.h, world_map_affine.h) and measured in node with test probes (port_work only).

**BG mode and layers.** DISPCNT mode 2. BG3 (char block 2, screen block 8) is the ground, BG2 (char block 3, screen
block 10) the mountains, woods and cliffs in front; both affine, 512 x 512 px, wrapping, priority 2, 256 colours.
BG1 (screen block 5, tile 127) and BG0 (windows) are not shown in mode 2. BG2CNT 0xaa0e, BG3CNT 0xa80a, BG1CNT 0x501.

**Perspective.** Each of the 160 lines is one straight strip of the flat map. `WorldMap_BuildScanlineTable` (only when
the pitch changes) gives each line a width scale and a ground distance (16.16, in heap slot 7's
`struct WorldMapAffineWork`); `Transform_UpdateVertices` (a routine copied to RAM, heap slot 46) turns them each frame
into a page of 160 x {BG2PA, PB, PC, PD, BG2X, BG2Y, the same for BG3} (two pages, frame parity), and
`WorldMap_ApplyAffinePage` (VBlank task) writes line 0's eight words by hand and starts DMA 0, HBlank, repeat, 8 words
to BG2PA..BG3Y for the rest. The reference point is **absolute**: BG2X/Y = (followed point / 2 + the line's offset) in
20.8, so a sample's unwrapped BG pixel is world position / 2 (measured: line 0's centre column = the followed x).
**Horizon/sky**: lines whose ray misses the ground get scale and distance 0 (pa = pc = 0, the reference at the
followed point: one texel stretched); with the game's pitch (7/8 turn, -45 degrees) the horizon is at line about -414,
far above the screen, so no sky line is ever on the GBA's screen in normal play. Holding L pulls the view back to 1.63 x
(`FieldEffect_RunVisibilityTransition`): the top line then reaches about 270 world units north of the party.

**Sprites.** Actors are projected (`ActorSystem_ProjectSprites` -> `Render_PlaceProjectedSprite`, sprite_draw.c), which
drops sprites outside screen x -32..272, y -32..208 (the GBA's screen), then OAM as on field maps. GS1 has no ship and
no clouds on its World Map; the sprites are the party leader and the scene's actors.

**Menus and events.** `WorldMap_StartStillPicture` draws the current view once into a 240 x 160 256-colour picture on
BG1 (BG1CNT 0x682, mode 0; the picture's tiles overwrite char blocks 2 and 3, the BG maps in screen blocks 8-11 stay);
menus and messages are drawn over it; `WorldMap_LoadAreaGraphics` brings the moving view back. R's world picture uses
the same BG1 setting but its own picture and palette and turns BG2/BG3 off (DISPCNT 0x1340). Opening the World Map and
closing it for R animate a letterbox (WorldMapView windowTop 80 -> 0, mode 0 outside the band).

**The key unknown: is the land around the view loaded?** Yes, well beyond the GBA's view:
- RAM (`Ram_CellPictures` 0x02020000): per layer a 2 x 2 block of world tiles (a tile is 16 x 16 cells of 32 world
  units = 512 units), chosen 256 units left of and 320 above the followed point, so it always holds at least
  x - 256 .. x + 256 and z - 320 .. z + 192 (it is 1024 x 1024 units). New quarters are decoded one a frame
  (`WorldMap_PreloadCurrentTileBlock`; `quarterTiles[]` says which tile each quarter holds, `tileIds[]` which it should).
- VRAM: each layer's 512 x 512 px BG map is the same 1024 x 1024-unit toroid (32 x 32 cells); the whole block is drawn
  when the World Map starts, then one cell column (16 units ahead of 256 units left/right) or row (192 units south, 288
  north) is redrawn as the view crosses 16-unit lines. So the BG holds the right cells at least 256 units left and right,
  288 north and 192 south of the view, and in practice the whole block.
- Measured (near Vale, pitch -45 degrees, no L): the GBA's top line covers z - 166 and x +- 146, its bottom line z + 79,
  x +- 106. At Most the extra 48 columns and 32 rows reach about z - 235 and x +- 204 at the top, z + 115 at the bottom:
  inside the loaded block. With L held the top margin rows at Most reach about z - 350: still inside the RAM block
  near Vale (it starts at z - 693 there), but past the 288 units the game guarantees.
- So nothing needs streaming; the renderer can check each margin sample. Per frame it compares every cell of both BG
  maps with the RAM cell it should show (cell picture -> its four tile entries, as `WorldMap_WriteLayerCellTile`
  writes them) and checks that the sample's world position is inside the RAM block and that its quarter is decoded
  (`quarterTiles == tileIds (+320 for layer 1)`). A sample that passes shows exactly what the game has for that place;
  any other is transparent (backdrop, black). The GBA's own pixels are never checked or changed.

**Can the extra lines be computed in the renderer?** Yes. On a line the strip is straight, so the extra columns are
the hardware's own stepping (BG2X + n * BG2PA) continued. Down the screen every term of a line (PA, PC, X, Y) is
`a + b / (line - h)` (h the horizon line: the scale is proportional to 1 / (line - h) and the distance is affine in the
scale). Three of the frame's own lines (0, 80, 159, as the DMA feeds them) give h and a, b for each term, exact at lines
0 and 159; measured on the game's lines the model is within 0.3 px (the game's own rounding of PA to 8.8), and fitted on
lines 0-79 it predicts lines 80-159, 80 lines away, within about 1 px (32 lines away much less). Rows past the horizon
(none in normal play) are transparent. Nothing in the game is changed or called.

Conclusion: **feasible in the renderer, without game-logic changes.** One culling test changes, as GS29's did:
`Render_PlaceProjectedSprite`'s screen bounds widen by gPortZoomL/R/T/B (0 at Normal and off the zoomed screens), so the
actors in the margins are projected into OAM.

## 2. Phase 2: what was built

On `main`: fc337a4 (renderer + one culling rule), b8473a3 (expected.tsv), a1f42b4 (web_opts --worldmap), then the docs.
No new option: the World Map follows the existing Map zoom setting (gs-zoom; Normal is untouched).

**Renderer** (port/pc/ppu.c, the GS1 branch only, in its own block after Port_PpuVBlank: `wm_*`, `worldZoom`,
`worldStill`; GS29's field code is changed only where the two must agree: `sZoomOn` in the margin black test, the frame
decision in Port_PpuLine, the deferred top rows, BG1's fill on World Map lines in mode 0). The World Map does **not**
use GS29's `zoom_offset` frame clamp: the GBA's lines sit at the frame's centre every frame (XO = 24/48, YO = 16/32), so
the picture cannot move when the camera stops or turns; only the game's own odd/even half-texel sampling changes between
frames, in the margins as in the GBA's view.
- **Which frames**: inside the field sequence, BG2CNT/BG3CNT the World Map's (priority bits ignored), DMA 0 an
  HBlank repeat of 8 words into BG2PA, gMapGridWork[0] in RAM. Moving view: BG1CNT not 0x682 (the letterbox opening and
  the encounter's centre line included). Still picture: BG1CNT 0x682, mode 0, BG2 and BG3 on, and a moving frame kept
  since the World Map started. Everything else (R's world picture: BG2/BG3 off; battles; towns...) is as before.
- **Margins of the moving view**: GBA lines: their own PA/PC/X/Y continued across (`wm_layer`, real rows); the rows above
  and below: the fit of section 1 (`wm_fit`, `wm_row`), from lines 0, 80, 159 (or the first ground line if the top is
  sky); top rows are drawn after line 159 with line 0's display registers (a copy of I/O 0x00-0x5f), bottom rows with
  line 159's. Each margin sample passes `wm_ok` (RAM block, quarter decoded, cell check from `wm_scan`) or is
  transparent: the backdrop (black). The cell checks need the cell-picture table that the still picture borrows for a
  frame on each side of a menu; while the BG maps and RAM cells are unchanged since the last moving frame its checks
  are kept, so the margins do not flash black when a menu opens or closes.
- **Plain layers** on World Map lines in mode 0 (BG1's tile-127 fill, the centre line of the encounter transition, the
  letterbox) go on past the GBA's screen as the hardware wraps them; BG0 (windows, messages) stays the GBA's 240 x 160.
- **Still picture (menus, events)**: the last moving frame's BG maps (screen blocks 8-11), tiles (char blocks 2-3), RAM
  cells, line terms and checks are kept (48 KB copied per moving frame); the margins show that ground as layer BG1 (its
  priority, windows, blending: BG1's), with the live palette and the live sprites.
- **Sprites**: OAM and the margin rows as GS29; `Render_PlaceProjectedSprite`'s bounds (-32..272, -32..208) widen by
  gPortZoomL/R/T/B (port/c_rules.tsv), so actors in the margins are projected. All four are 0 at Normal and on every
  240 x 160 screen, which leaves the test as the original.

**What stays 240 x 160 and why**: R's world picture (a different picture, not the view: the game turns BG2/BG3 off and
loads its own palette), battles, the title/File Screen and every other screen, as in GS29. The window layer (menus,
messages) stays the GBA's 240 x 160 in the middle of the frame.

**Truthful, not complete**: margin samples outside the loaded block are black. Near Vale nothing is black in normal
play; with L held at Most the far top corner of the frame can pass the block's edge (the contact sheet's last frame:
a black corner over the sea north of Mercury Lighthouse). Rows past the horizon would be black; the game's pitch puts
the horizon about 414 lines above the screen, so none are seen.

**Ships, clouds**: GS1's World Map has neither (the ship to Tolbi is a scene, not a World Map actor).
